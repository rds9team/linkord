# Linkord 機能仕様書

## 1. URL設計

```text
/                         ランディングページ
/login                    認証方法選択
/@:username               認証済みプロフィール
/@:username-:code         未認証プロフィール
/settings                 プロフィール設定
/settings/media           メディア設定
/settings/servers         サーバー設定
/settings/connections     認証プロバイダ設定
/discover                 サーバー・プロフィール発見
/server/:slug             サーバー詳細
/report                   通報
/admin                    管理画面
```

未認証プロフィールのURL例：

```text
https://linkord.net/@yuto-4821
```

`#`はURLのフラグメントとして扱われるため、未認証プロフィールのURLには使用しない。

---

## 2. 認証プロバイダ

対応予定：

- Discord
- GitHub
- Google
- LINE
- Microsoft
- Roblox
- メールログイン
- 未認証アカウント作成

### 認証方針

- 未認証でもプロフィールを作成できる
- Discordなどの認証は必須にしない
- 1つのLinkordアカウントに複数の認証方法を連携できる
- 同じ認証プロバイダのアカウントを複数のLinkordアカウントに連携できない
- 認証プロバイダの表示名をそのままURLに使用しない
- 認証情報はプロバイダ固有IDで管理する
- OAuthアクセストークンを不要に長期保存しない
- OAuthの`state`を検証する
- 対応プロバイダは段階的に追加する

### 実装優先順位

1. 未認証アカウント
2. Discord
3. GitHub
4. Google
5. LINE
6. Roblox
7. Microsoft
8. メールログイン

- created_at
- updated_at
- last_login_at
- deleted_at

### account_identities

- id
- account_id
- provider
- provider_user_id
- provider_username
- created_at
- last_login_at

### 制約

- `provider`と`provider_user_id`の組み合わせは一意にする
- 認証情報の連携・解除時に本人確認を行う
- 最後のログイン手段は、別のログイン手段を追加するまで解除できない
- 退会時は関連データを削除または匿名化する
- 未認証アカウントには推測されにくい内部識別子を使用する

## 4. Discord OAuth2

### 要件

- Discord OAuth2の`identify`スコープを使用する
- 初回ログイン時にLinkordアカウントを作成する
- 既存ユーザーは既存アカウントへログインする
- Discord User IDを内部の認証IDとして保存する
- Discordのアクセストークンを不要に長期保存しない
- ログアウトできる
- Discord連携を解除できる
- 退会時にユーザーがデータを削除できる
- Discord OAuth2連携済みユーザーにDiscord Authedバッジを付与する

### 保存する基本情報

- Discord User ID
- username
- global_name
- avatar
- 作成日時
- 最終ログイン日時

Discordの表示名やユーザー名を変更しても、LinkordのURLは自動変更しない。

Discord Authedは、本人確認・身元確認・Discord公式認証を意味しない。

## 5. ユーザー名

### 認証済みユーザー

- ユーザー名はユーザー自身が決定する
- Discordユーザー名は初期候補として使用できる
- Discordユーザー名を必ずURLに使用する必要はない
- URLはLinkord内で確定したユーザー名を使用する
- 既に使用されているユーザー名は登録できない
- なりすまし、公式を誤認させる名前、禁止語は使用できない
- ユーザー名の変更にはクールダウンを設定できる

例：

```text
https://linkord.net/@yuto
```

### 未認証ユーザー

- 未認証でもプロフィールを作成できる
- ユーザー名は自由入力
- システムが4桁の数字を生成する
- 数字は暗号学的に安全な乱数で生成する
- 同じURLが存在する場合は再生成する
- DBにユニーク制約を付ける
- 数字部分はユーザーが任意に変更できない
- 認証後、ユーザーが希望すれば短いユーザー名へ移行できる
- 未認証プロフィールは一定期間ログインがない場合に削除対象にできる

例：

```text
https://linkord.net/@yuto-4821
```

### 要件

- DBには`theme_id`のみを保存する
- テーマ定義は共通静的アセットとして配信する
- ユーザー入力によるCSSやJavaScriptを実行しない
- テーマごとに許可された設定だけを使用する

## 8. メディア

### 対応形式

- JPEG
- PNG
- WebP
- GIF
- MP3
- OGG
- WAV
- MP4
- WebM

### 初期制限

- 画像：1ファイル最大10MB
- 音楽：1ファイル最大20MB、最大10分
- 背景動画：1ファイル最大50MB、最大60秒
- ユーザーごとの合計容量：設定値で管理する
- 1日あたりのアップロード回数を制限する

### 要件

- MIMEタイプを検証する
- 拡張子だけを信用しない
- ファイルの実体を検証する
- ファイル名をそのまま保存しない
- ランダムまたはハッシュベースのファイル名を使う
- 実行可能ファイルを拒否する
- ユーザー自身が削除できる
- 管理者が削除できる
- アップロード先でファイルを実行できないようにする
- アプリケーション本体とアップロード保存先を分離する
- 不正なファイルを管理者が削除できる

初期保存先はVPSとする。

将来のR2移行に備え、保存処理はストレージ抽象化層を経由する。

- Spotify
- ゲームアクティビティ
- カスタムステータス
- その他のアクティビティ

### 要件

- 非公開・取得不能な情報を無理に表示しない
- Lanyard APIの障害時はエラー表示ではなく、非表示または最終取得値を使用する
- 外部APIの応答をそのまま信用せず、必要な項目だけを保存・表示する

### 自動タグ

- Spotify再生中 → Music
- Minecraft起動中 → Minecraft
- VS Code起動中 → Developer
- 配信中 → Streaming

手動タグと自動タグは内部的に分ける。

例：

### 取得方式

```text

  ↓

  ↓

  ↓

```

### 要件

- ゲームモード別にキャッシュする

- APIエラー時は最終取得データを表示できる
- データがない場合は「データなし」と表示する
- 最終取得時刻を表示する
- PlayHive API停止時もプロフィールを表示する
- 外部APIのデータ取得失敗でプロフィール全体を壊さない

### 種類

- 急上昇
- ジャンル別
- 言語別
- Minecraft
- 日本語

```text
trend_score =
  views_24h
  + boosts_24h * 10
```

- 新着・小規模サーバーにも露出枠を提供する

- 管理者が不正なスコアを無効化できる

## 13. ブースト

### 要件

- 1ユーザーは同じサーバーに1時間に1回だけブーストできる
- ブーストはサーバーのランキングスコアに反映する
- 不正ブーストは管理者が無効化できる
- IPだけでなくユーザーID単位でも制限する
- 未認証ユーザーのブースト可否は設定で変更できる
- 自分のサーバーへの過剰なブーストを検知する
- ブースト履歴を必要最小限保存する

## 16. バッジ

### バッジ

- 灰色：Discord Authed
- 青色：Supporter
- 金色：Team
- 紫色：Founder

### 色

```css
--badge-discord-authed: #8b949e;
--badge-supporter: #3b82f6;
--badge-team: #f5b942;
--badge-founder: #a855f7;
```

### 要件

- Discord AuthedはDiscord OAuth2連携済みユーザーに自動付与する
- Discord Authedは本人確認を意味しない
- Discord AuthedはDiscord公式認証を意味しない
- Supporterは開発支援者に管理者が任意で付与する
- Teamはrds9teamまたはLinkord運営メンバーに管理者が付与する
- FounderはLinkord創設者に管理者が付与する
- TeamとFounderは一般ユーザーが自分で付与できない
- Discord公式バッジと誤認させない独自デザインにする
- ユーザーはバッジ表示を非表示にできる
- 非表示設定は本人のプロフィール表示だけに適用する
- バッジの表示・非表示に関係なく、内部的な付与状態は保持する

### 表示形式

- 塗りつぶしの円の中に白い`✓`を表示する
- 円の色は上記のカラートークンを使用する
- Discord公式の認証バッジと同一・類似のデザインにしない
- アイコンには`alt`属性またはアクセシブルなラベルを付ける
- ホバー時にバッジ名を表示する
- スマートフォンではタップまたはアクセシブルなラベルで確認できるようにする

例：

```text
灰色の✓ → Discord Authed
青色の✓ → Supporter
金色の✓ → Team
紫色の✓ → Founder
```

`rds9`認証アイコンを使用する場合は、Discord公式認証を意味しない独自アイコンとして扱う。

## 17. 開発支援

PayPay送金リンクを使用する。

### 支援ボタン

```text
Linkordを応援する
```

### 支援ページの説明

```text
Linkordのドメイン代・サーバー代などの維持に使われます。
支援は任意で、支援しなくても基本機能を利用できます。
```

### 要件

- 支援は完全に任意とする
- 支援しなくても基本機能を利用できる
- 支援によって主要機能を制限しない
- 支援金はドメイン・サーバー・バックアップなどの運営費に使用する
- 支援額は公開しない
- 支援者名は本人が希望した場合のみ公開する
- 支援は有料プランや機能購入ではない
- Linkordは送金完了、送金額、送金者を自動検証しない
- Supporterバッジは管理者が任意で付与する
- PayPay通知を使用する場合も、開発者向け通知として扱う
- PayPayの送金完了をLinkord上の自動認証に使用しない

## 18. Supporterのユーザー名優先権

- Supporterは、一般公開前の未使用ユーザー名を優先して予約できる
- 既に他ユーザーが使用中のユーザー名は取得できない
- Discord公式アカウントや他人になりすます名前は予約できない
- 禁止語や不適切なユーザー名は予約できない
- 予約後、一定期間ログインがない場合は解放できる
- Supporter資格を失った場合も、取得済みユーザー名は原則維持する
- ユーザー名の取得・永久保持・特定名称の確保を保証しない
- ユーザー名の優先予約は、任意の運営支援への感謝として提供する
- ユーザー名の譲渡・販売を禁止する

## 19. Google Analytics

ユーザー自身のGoogle Analytics測定IDをプロフィールに登録できる。

### 要件

- 測定IDはユーザー自身が所有するものに限る
- 許可する形式を`G-XXXXXXXXXX`などに制限する
- 任意のJavaScriptや外部スクリプトURLは許可しない
- Google Analyticsの公式スクリプトのみ使用する
- 管理者は登録された測定IDを確認できる
- 未設定時はユーザー用Analyticsを読み込まない
- プロフィールにAnalytics使用中であることを表示できる
- Content Security Policyを設定する
- ユーザー入力のJavaScriptを実行しない

## 22. セキュリティ

- 秘密情報をソースコードに直書きしない
- `.env`をGitにコミットしない
- 本番環境と開発環境の認証情報を分離する
- OAuthの`state`を検証する
- OAuthコールバックURLを厳密に制限する
- CSRF対策を行う
- XSS対策を行う
- SQLインジェクション対策を行う
- SSRF対策を行う
- レート制限を実装する
- ファイルアップロードを検証する
- 管理操作を監査ログに記録する
- DB変更にはマイグレーションを用意する
- 個人情報を必要以上に保存しない
- 外部APIの応答を信用しすぎない
- アカウント削除時に関連データを削除する
- 未認証アカウントの乗っ取り対策を用意する
- セッションCookieに`HttpOnly`、`Secure`、`SameSite`を設定する

## 24. 実装ルール

- 既存仕様を勝手に変更しない
- 仕様にない機能を追加しない
- 不明な仕様を推測で確定しない
- 未実装部分を実装済みとして報告しない
- 外部APIに依存してプロフィール本体を壊さない
- 秘密情報をコードに直書きしない
- DB変更にはマイグレーションを用意する
- 正常系と異常系の両方を確認する
- 実装後に変更ファイルを報告する
